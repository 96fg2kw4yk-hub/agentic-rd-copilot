Agentic R&D CopilotV3 源码深度解析

一句话定位：这是一个基于 LangGraph 多 Agent 编排的 AI 驱动代码修复系统。给定一个 Issue（Bug 描述），系统自动完成：理解问题 → 检索相关代码 → 定位 Bug 位置 → 生成修复 Patch → 运行测试验证 → 生成 Pull Request。

校招面试价值 这个项目覆盖了 LLM 应用开发中最核心的五个领域：Agent 编排、RAG 检索增强、代码理解（AST）、系统工程（FastAPI）、评测体系。是展示 AI 工程能力的绝佳项目。

设计思想与动机

为什么要做这个项目？

在企业中，一个完整的 Bug 修复流程通常要经过：看 Issue → 理解问题 → 找到对应代码 → 写修复 → 跑测试 → 提交 PR。这个过程中，最耗时的是「定位代码」和「理解上下文」。这个项目让 LLM 来串起整个链路，把人从重复劳动中解放出来。

核心设计决策**

决策①：为什么用 LangGraph 而不是手动编排？

LangGraph 提供了 状态图（StateGraph）+ 条件边（conditional edge） 的能力。在 V1 只有 3 个节点，手动写串行调用很简单；但 V3 扩展到 6 个节点后，需要支持 "基础模式" 和 "全链路模式" 的分支决策。LangGraph 的 conditional_edges 天然支持这种分支，比 if-else 更可维护和可扩展。同时 StateGraph 的状态传递机制保证了每个节点都能访问全量上下文。

决策②：为什么混合检索（BM25 + 向量 + 结构化）？

纯向量检索在代码场景有严重缺陷：变量名 token 和 jwt_token 在语义上很近，但纯关键词匹配可能更精确。反过来，Issue 中说 "登录失败"，向量检索能找到语义相关的代码如 authenticate、verify_password，而 BM25 的关键词匹配则很难建立这种关联。两种方法互补：BM25 保证精确匹配（函数名、错误码），向量检索保证语义覆盖。结构化分数（路径匹配、函数名匹配）则是代码领域的先验知识注入——比如 Issue 提到 "auth"，那么 auth.py 文件天然应该加分。

决策③：为什么每个 Agent 都设计了 fallback？

LLM 会挂（Ollama 服务宕机、模型超时、返回格式错误），但系统不能跟着挂。每个 Agent 都有 try-except + degenerated logic。比如 IssueAnalyzer 在 LLM 不可用时用正则做退化分析（匹配"AttributeError"、"500"等），PatchGenerator 在 LLM 失败时生成基础 diff 框架。这是生产级 AI 系统的基本素养——永远有 Plan B。

决策④：AST 解析 vs 纯文本分段

代码不是普通文本。如果按固定行数切分代码（如每 100 行一段），很可能把函数拦腰截断。AST 解析能语义感知——以函数、类为最小单元切割，每个 chunk 是有意义的代码片段。同时 AST 还能提取 import 关系、参数列表、装饰器等结构化信息，这些在后续检索和推理中都很关键。

设计要点：

① 路径全部基于 BASE_DIR 动态计算，而不是写死绝对路径。这保证了项目的可移植性——换一台机器 clone 下来就能跑。

④ 为什么 BM25:向量:结构化 = 4:4:2？ 这不是拍脑袋的。BM25 和向量各占 40% 是因为它们在代码检索中互补性最强；结构化占 20% 是因为路径/函数名匹配不能太重，否则会掩盖真正的语义相关性。实际项目中这个比例应该通过 A/B 测试来调优。

ast_parser.py — AST 代码解析器

面试考点 Python AST 模块的理解、代码结构化提取

核心数据结构：CodeChunk

@dataclass
class CodeChunk:   # 代码片段的结构化表示
    chunk_id: str           # 全局唯一 ID："{repo_id}:{file_path}:{symbol_name}"
    repo_id: str
    file_path: str
    symbol_type: str        # "file" | "class" | "function" | "method" | "test"
    symbol_name: str        # 函数名/类名
    start_line: int
    end_line: int
    content: str            # 原始代码
    summary: str            # 自动生成的摘要
    docstring: str
    imports: list[str]
    parent_class: str       # 如果是方法，记录所属类名
    decorators: list[str]   # @pytest.mark.skip 等
    params: list[str]       # 参数名列表
    returns: str

为什么选择 dataclass 而不是 dict？ dataclass 有类型提示，IDE 能自动补全和检查。相比之下，dict 的 key 是字符串，容易拼错，IDE 也帮不了你。在大型项目中，dataclass 的可维护性远好于 dict。

核心方法：parse_file()

def parse_file(self, repo_id, file_path, source_code) -> list[CodeChunk]:
    chunks = []
    # 1. 文件级 chunk —— 整文件概览
    file_chunk = CodeChunk(symbol_type="file", ...)
    chunks.append(file_chunk)

    # 2. AST 解析
    tree = ast.parse(source_code)

    # 3. 提取 import
    all_imports = self._extract_imports(tree)

    # 4. 遍历顶层节点
    for node in ast.iter_child_nodes(tree):
        if isinstance(node, ast.FunctionDef):     # 顶层函数
            chunks.append(self._parse_function(...))
        elif isinstance(node, ast.ClassDef):      # 类
            chunks.append(self._parse_class(...))
            for item in node.body:                # 类内方法
                if isinstance(item, ast.FunctionDef):
                    chunks.append(self._parse_function(..., parent_class=node.name))

关键设计：三层 chunk 结构

① 文件级 (file)： 每个 .py 文件生成一个概览 chunk，包含前 2000 字符和所有 import。这能让后续检索时，即使用户搜的关键词只在文件名中出现，也能命中。

② 类级 (class)： 类定义单独一个 chunk。这样 "修改 User 类的某个方法" 这种 Issue 能直接命中。

③ 函数/方法级 (function/method)： 这是最细粒度的 chunk，是 Bug 定位的最终目标。每个函数都是独立的检索单元。

④ 测试识别： symbol_type = "test" if func_name.startswith("test_") —— 根据命名约定自动识别测试函数，后续检索时可以区分业务代码和测试代码。

chunk_id 的命名设计

chunk_id = f"{repo_id}:{file_path}:{symbol_name}"
# 例如: "ab12cd34:src/auth/login.py:validate_token"

这个 ID 包含三级信息：哪个仓库 → 哪个文件 → 哪个符号。在混合检索时，不同来源（向量和 BM25）的结果都通过 chunk_id 对齐，这是多索引合并的基础。

面试话术："我用 Python 内置的 ast 模块做代码的结构化解析。核心思路是把代码拆成三层 chunk——文件级、类级、函数级——每一层都是一个独立的检索单元。这样做的优势是检索粒度可配：粗粒度搜索用文件级，精确定位用函数级。同时我从 AST 中提取了 imports、参数列表、装饰器等结构化元数据，这些信息在后续 LLM 推理时提供了丰富的上下文。"

关键设计点逐一拆解：

① 为什么要做分数归一化？ 向量检索返回的是 L2 距离（越小越好），BM25 返回的是相关性分数（越大越好），两者的值域完全不同（BM25 可能 0-50，向量距离可能 0-2）。不做归一化直接加权，某个检索源的分数会淹没另一个。归一化后都映射到 [0, 1]，才能公平加权。

② 为什么先各取 top_k*2 再合并？ 这叫「过检索再重排序」。如果只取 top_k，可能某个非常好的候选只在向量或只在 BM25 中排名 top_k 以内，但在合并后能排进前几名。多取一倍是为了给合并阶段更大的候选池，提高召回率。

③ 结构化分数怎么设计的？ 这是代码领域的先验知识编码。如果 Issue 中的词直接出现在函数名（如 Issue 说 "decode"，函数叫 jwt_decode()），这是强烈信号，加 0.3。如果出现在文件路径中（如 "auth" 匹配 auth/login.py），稍弱但仍有意义，加 0.2。如果文件路径包含 "test"，稍微微调 0.1。这些权重不是从数据中学的，而是根据经验设定的规则。

④ 为什么向量和 BM25 各占 0.4？ 0.4+0.4+0.2=1.0，三个分数构成互补体系。BM25 保证精确命中（如函数名精确匹配），向量保证语义覆盖（如 "login failed" 能匹配到 authenticate()），结构化保证代码特有的层级相关性。4:4:2 是经验值，可以通过评测模块调优。

面试话术："混合检索的核心思想是取长补短。向量检索擅长语义理解——'登录失败'能匹配到 authenticate 函数——但对精确名称匹配不够敏感。BM25 恰好相反，对函数名、类名这些精确符号非常灵敏。我的做法是先分别检索后合并，关键步骤有三个：分数归一化（统一到 [0,1] 区间）、过检索扩大候选池（各取 k*2）、以及加入领域先验的结构化分数（函数名匹配 +0.3，路径匹配 +0.2）。最终按加权分数重排序返回 Top-K。"

issue_analyzer.py — Issue 分析 Agent

class IssueAnalyzer:
    def analyze(self, issue_text) -> dict:
        # Step 1: 用正则预提取错误堆栈
        error_stack = self._extract_error_stack(issue_text)
        # Step 2: LLM 结构化分析（关键词、模块、严重程度...）
        response = self.llm.invoke([SystemMessage(...), HumanMessage(prompt)])
        result = json.loads(response.content)
        # Step 3: 如果 LLM 失败，fallback 到纯规则分析
        except: result = self._fallback_analyze(issue_text)

设计要点：

① 为什么用 temperature=0.1 而不是 0？ 过低的 temperature 有时会让 LLM 陷入重复循环。0.1 在确定性输出和灵活性之间取得平衡——足够稳定输出 JSON，又不会僵死。

② 为什么先正则提取、再 LLM 分析？ 正则提取不依赖 LLM，零延迟、零成本。先把明显的错误堆栈摘出来，既减少了 LLM 需要处理的文本量，又能把正则结果作为 LLM 分析的"锚点"——哪怕 LLM 分析结果有偏差，错误堆栈信息仍然是准确的。

③ fallback_analyze 的实现思路： 纯规则系统。匹配 Python 内置异常名（AttributeError、KeyError...）、HTTP 状态码（4xx/5xx）、技术关键词（JWT、auth、database...），然后根据关键词组合判断严重程度。这保证了系统在最坏情况下仍然有基本的分析能力。

④ 为什么输出强制 JSON 格式？ JSON 是结构化数据，下游 Agent 可以可靠地解析字段。如果 LLM 直接输出自然语言，下游解析会非常脆弱。Prompt 中说「只返回 JSON，不要其他文字」就是在约束输出格式。

关键设计：定位结果不止是排序列表

如果只返回一个文件列表（如 ["auth.py", "middleware.py"]），用户不知道为什么选中了这些文件。BugLocator 多走了一步：让 LLM 阅读排序后的结果，生成自然语言的解释——「哪个文件最可能是 Bug 源头？为什么？建议从哪里开始排查？」。这就是 RAG 中 "G"（Generation）的价值——不仅检索，还要给出可解释的答案。

        workflow.add_conditional_edges(
            "locate_bug", decide_mode,
            {"generate_patch": "generate_patch", "done_basic": END}
        )
    return workflow.compile()

条件边的设计模式： add_conditional_edges 接收一个决策函数 decide_mode，该函数读 state 返回一个决策字符串，然后映射到不同的下一节点。这实现了 "基于状态的动态路由"——同一个节点完成后，根据 state 的 mode 字段走不同分支。这是 LangGraph 相比于硬编码 if-else 链的核心优势。

V1 vs V3 的巧妙实现： V1（basic）和 V3（full）共享同一个图结构，通过 mode 参数控制是否添加 Patch/验证/PR 三个节点。这是一个优雅的设计：不需要维护两套图，只需要一个参数切换。

每个 Node 函数的模式

def analyze_issue_node(state: PipelineState) -> PipelineState:
    print(f"[Workflow] ① Issue 分析: ...")
    state["issue_analysis"] = issue_analyzer.analyze(state["issue_text"])
    state["status"] = "issue_analyzed"
    return state   # 返回更新后的状态

LangGraph 的节点函数遵循函数式编程：输入 state → 修改 state → 返回 state。状态是不可变更新的——你返回一个新的 state dict，LangGraph 负责合并。这样每个节点都可以看全量上下文，不依赖全局变量。

设计要点：

① Pydantic 请求模型： 每个 API 都有对应的 BaseModel 子类定义输入格式，FastAPI 自动做参数校验和类型转换。这比手动 request.json() + 字段检查的方式安全得多，也是 FastAPI 的最佳实践。

② 异步任务模式： 分析是耗时操作（LLM 调用可能好几秒），所以 POST 请求先创建 task_id 并立即返回，用户可以 GET task 结果。这是一个简单的异步模式，虽然没有用 Celery 那么重，但在 V1 阶段够用。

③ 内存字典做任务存储： tasks: dict[str, dict] = {} 用内存字典存任务状态，注释明确写了"后续可换数据库"。这是一个务实的工程决策——先跑通再优化，不要在 V1 阶段过度设计。（面试时提这一点很加分）

④ repo_map 做二级查找： 索引后的仓库可能不在内存中，所以 API 会先从内存 map 找，找不到再扫描磁盘。这个容错设计确保了服务重启后仍能正常工作。

设计约束（写在注释里）：

① 只能修改 Top-K 文件 → 防止 LLM 过度修改，确保改动最小化

② 必须输出 unified diff 格式 → 标准格式，可直接被 git apply 使用

③ 必须说明修改原因和风险 → 让人类 review 时有据可依

④ 不允许大规模重构 → 每个 Patch 应该只解决当前 Issue，不做额外优化

这些约束反映了工程实用性——在真实生产环境中，你的 Patch 要被别人 review，破坏性太大会被 reject。

fallback diff 的逻辑： 当 LLM 不可用时，生成一个基本的 diff 框架（标注修改位置和提示）。这保证了系统在任何情况下都有输出，不会白屏。

pr_agent.py — PR 生成 Agent

PR Agent 的逻辑相对简单，本质上是一个信息聚合 + 格式化的角色。它从上游四个 Agent（Issue分析、Bug定位、Patch、验证）拿结果，合成一份专业的 PR 文档。核心 prompt 要求输出：PR 标题（英文、50字以内）、详细描述（中文）、CheckList 审查项。

test_runner.py — 测试执行器

def _run_command(self, cmd, cwd, tool_name):
    proc = subprocess.run(cmd, cwd=cwd, capture_output=True, text=True, timeout=60)
    return {"status": "passed" if proc.returncode == 0 else "failed", ...}
    except subprocess.TimeoutExpired: return {"status": "timeout", ...}
    except FileNotFoundError:         return {"status": "skipped", ...}

三种状态设计：passed / failed / skipped——tool 没安装时不报错，返回 "skipped" 并标注原因。这是 "graceful degradation"（优雅降级）的体现。

为什么用 subprocess 而不是 Python API？ pytest、ruff、mypy 都是命令行工具，通过 subprocess 调用和开发者在终端里运行完全一致。如果用 Python API，行为和命令行可能不同，导致「本地跑能过但 CI 失败」的情况。

benchmark.py — 评测模块

面试考点 模型评测指标的设计
class Benchmark:
    def evaluate_localization(self, predicted_files, ground_truth_file):
        rank = None
        for i, f in enumerate(predicted_files):
            if ground_truth_file.endswith(f) or f.endswith(ground_truth_file):
                rank = i + 1; break
        return {
            "top1": rank == 1,      # 第一名就命中？
            "top3": rank <= 3,      # 前三名命中？
            "top5": rank <= 5,      # 前五名命中？
            "reciprocal_rank": 1.0 / rank if rank else 0.0,  # MRR
        }

四个核心指标：

① Top-1/3/5 Accuracy： 真实 Bug 文件在预测列表前 1/3/5 名中的概率。Top-1 是最严苛的（必须一次命中），Top-5 更宽松（给系统一定的容错空间）。在面试中报告时可以这样：「在我们的 benchmarks 上，Top-3 准确率是 X%，意味着 3 次点击内能找到 Bug 的概率是 X%。」

② MRR (Mean Reciprocal Rank)： 倒数排名的均值。如果 Bug 排第 1 名，MRR 贡献 1.0；排第 2 名贡献 0.5；排第 10 名贡献 0.1。MRR 综合反映了「系统有没有把真正相关的排在前面」。比单纯 "命中与否" 更细致。

面试话术："我设计了四个评测指标来评估 Bug 定位效果。Top-K 准确率反映的是用户实际体验——几次点击能找到 Bug；MRR（Mean Reciprocal Rank）更细致地衡量排序质量——系统有没有把正确答案放在尽可能靠前的位置。此外还可以扩展评估 Patch 是否可 apply、测试是否通过等端到端指标。评测体系的设计关键是：指标要能反映真实的用户体验，不能只是纸面数字。"

frontend/index.html — Web 前端

前端用了零框架方案——纯 HTML + CSS + JS，没有任何 React/Vue/构建工具。这样做的原因：项目定位是 AI 工程而非前端项目。一个单文件 HTML 足够展示功能，而且部署极简（不需要 npm build，直接 serve）。

不过，前端有几个值得提的设计：

① CSS 变量做主题： 所有颜色通过 :root 下的 CSS 变量（如 --bg、--accent）管理，而不是硬编码。换暗色/亮色主题只需改几个变量。

② Pipeline 步骤可视化： 6 个步骤的进度条用 CSS class 切换（active/done/fail），直观展示当前进度。

③ 健康检查轮询： setInterval(health, 30000) 每 30 秒检查后端是否在线，状态指示灯实时更新。

🎯 校招面试备战

面试官可能会问什么？

面试官通常是后端/AI 方向的资深工程师。对于一个 AI Agent 项目，他们关心的不是"你用了什么工具"，而是「你为什么这样设计？」「遇到什么问题？怎么解决的？」「如果让你重做，哪里会不一样？」

以下按高频考点分类整理了 15 道面试题及参考答案。

一、架构设计类问题

Q1: 这个项目的整体架构是怎样的？各模块如何协作？

参考回答：

这是六层架构。最上层是 Web 前端，中间是 FastAPI 做请求路由，核心是 LangGraph 编排的 6 个 Agent 组成的有向无环图。每个 Agent 是独立职责的 LLM 调用单元——Issue 分析 Agent 理解问题，检索 Agent 找相关代码，Bug 定位 Agent 确定位置，Patch 生成 Agent 写修复，测试执行器验证修复，PR Agent 生成 Pull Request。底层是混合检索引擎（BM25 + 向量 + 结构化分数），为 Agent 提供代码检索能力。

设计上的关键决策是分层解耦：每一层只依赖下一层的接口，不跨层调用。比如 Bug 定位 Agent 不直接读磁盘文件，而是通过 Indexer 的 hybrid_search 接口获取检索结果。这样如果未来想换检索方案（比如从 ChromaDB 换到 Milvus），只需要改 Indexer，Agent 代码不动。

Q2: 为什么选择 LangGraph 做编排而不是自己写一个简单的串行调用？

参考回答：

有三个核心原因。第一，LangGraph 的 StateGraph 提供了声明式的状态管理——所有 Agent 的输入输出都通过统一的 state 字典传递，而不需要手动维护全局变量。第二，条件边（conditional_edges）让流程分支变得优雅——我的项目有 V1（基础）和 V3（全链路）两种模式，条件边可以根据 state.mode 动态决定下一步走哪个节点，如果硬编码 if-else 链，复杂度会随节点数指数增长。第三，可扩展性：这是一个 6 节点的 DAG，未来可能扩展更多节点（比如自动回滚、A/B 测试等），LangGraph 的图结构天然支持这种扩展——只需要 add_node + add_edge，不影响已有逻辑。

Q3: V1 有哪些问题？你做的 V3 改进了什么？

参考回答：

V1 只覆盖了 Issue 分析 → 检索 → 定位这三步，到这里就停了。实际上找到 Bug 只是第一步，还要修复、验证、提交 PR。V3 扩展了后三步——Patch 生成、测试验证、PR 生成——形成了一个完整的闭环。另一个关键改进是评测体系：V1 没有评测，你无法量化系统的好坏；V3 加入了 Benchmark 模块，能计算 Top-K 准确率和 MRR，有了数据才能做 A/B 实验、调参数。最后是前端可视化——V3 的 6 步 Pipeline 进度条让用户实时看到系统在做什么，这是做 toB 产品很关键的用户体验。

二、检索引擎类问题

Q4: 你为什么做混合检索？只用向量检索不够吗？

参考回答：

纯向量检索在代码场景有两个致命缺陷。第一，精确匹配弱——Issue 里说 "jwt_decode function error"，向量检索可能因为语义相似把其他 decode 相关函数也拉出来，但 BM25 可以直接命中函数名。第二，代码中大量使用缩写、驼峰命名（如 getUserById），这些不是自然语言，嵌入模型的语义理解效果打折扣。反过来，纯 BM25 无法理解同义词——"登录失败" 和 "authentication error" 在人看来是同一个意思，但 BM25 只做词频匹配。所以我做了三路混合——BM25 负责精确命中、向量负责语义覆盖、结构化分数（函数名/路径匹配）注入代码领域先验。三个信号加权求和，取长补短。

Q5: 混合检索中为什么需要分数归一化？怎么做的？

参考回答：

归一化的必要性在于不同打分函数的输出值域完全不同。ChromaDB 返回的是 L2 距离（典型值 0.1-0.8），BM25 返回的是词频加权的相关性分数（可能是 0-50）。如果不归一化，假设 BM25 分数普遍在 30 左右，向量分数在 0.5 左右，那 40% * 30 会完全淹没 40% * 0.5——BM25 主导了最终排名，向量检索形同虚设。

我的归一化方案是 max-normalization——每个信号源都除以该源的最大分数，映射到 [0,1] 区间。这样做的前提假设是：同一次查询中，不同检索源返回的最高分 chunk"质量相当"，都是该源的最佳候选。如果这个假设不成立（比如某次向量检索结果都很差），可以考虑 min-max 归一化或者 rank-based 融合（如 Borda Count），这是未来的优化方向。

Q6: 如果让你改进检索系统，你会做什么？

参考回答：

几个方向。第一，用 reranker 做精排：现在混合分数是固定权重线性组合，可以用一个轻量级 Cross-Encoder（如 BGE-Reranker）对 Top-20 候选做二次排序，效果通常比线性融合好很多。第二，加入代码专用的嵌入模型：现在用的是通用嵌入模型 nomic-embed-text，换成 CodeBERT 或 UniXcoder 这种代码预训练模型，对代码的语义理解会好很多。第三，学习权重而非固定权重：4:4:2 是我拍脑袋的，可以通过 learning-to-rank 在评测集上学习最优权重。第四，加入依赖图检索——如果 Bug 在 auth.py，那 auth.py 的 import 依赖链上的文件也应该进入候选池，这是代码特有的结构化信息。

三、Agent 设计类问题

Q7: 你的 LLM 调用有什么最佳实践？

参考回答：

我总结了四个实践。一是 temperature 选择：分析类 Agent 用 0.1（接近确定性），创意生成类（如 PR 标题）用 0.2（稍微给点变化）。二是强制 JSON 输出：Prompt 中明确要求「只返回 JSON」，并做 Markdown 代码块清洗（去掉 ```json 标记），因为 LLM 经常在 JSON 外包代码块。三是 fallback 容错：每个 Agent 的 LLM 调用都包在 try-except 里，LLM 失败时走 rule-based 退化逻辑——比如 Issue 分析退化为正则匹配，Patch 生成退化为基础 diff 框架。四是 SystemMessage 设定角色：每个 Agent 都给 SystemMessage 设定了专业角色（"你是资深软件工程师"），这比只给 HumanMessage 的效果好得多，因为 SystemMessage 会影响 LLM 的语气和专业度。

Q8: 如果 LLM 生成的内容有错误（幻觉），你如何处理？

参考回答：

幻觉在 AI 应用中不可避免，关键是让系统在幻觉发生时不会造成破坏。我的策略是分层防御。第一层是输出格式约束——强制 JSON 输出，如果 JSON 解析失败就触发 fallback，不会让脏数据流到下游。第二层是内容约束——Patch 生成 Agent 明确要求只能修改 Top-K 文件中已有的代码，不能生成不存在的内容。第三层是验证层——Patch 生成后跑 pytest/ruff/mypy，如果有错误会被捕获并体现在 PR 的 risk_assessment 中，人类 reviewer 能看到「测试未通过」的标记。第四层是人工审核——所有 PR 都包含 risk_level 和 checklist，最终审核权在人类手里。核心思想是：AI 可以犯错，但系统要把错误控制在可检测、可回滚的范围内。

Q9: 你如何评估 Agent 的好坏？

参考回答：

我设计了分层评测。定位 Agent 用 Top-K 准确率和 MRR——能直接量化排序质量。但端到端的评测更难：Patch 是否真的 fix 了 Bug？这需要可复现的测试用例（Bug 引入前测试失败、Patch 后测试通过）。我在 benchmark.py 中预留了 run_benchmark 方法，可以对接标注好的 test_cases 数据集。PR 质量的评测更主观——标题是否准确、描述是否充分——目前依赖人工 review，未来可以用 LLM-as-Judge（让一个更强的模型打分）。核心观点：Agent 的评测不能只看一个指标，要从定位精度、修复质量、PR 可读性三个维度综合评估。

四、代码实现类问题

Q10: ast_parser 中如何区分函数和方法？怎么做错误处理？

参考回答：

函数和方法的差异不在 AST 节点类型（都是 FunctionDef），而在位置——顶层的是函数，在 ClassDef body 里的是方法。实现上，parse_file 遍历顶层节点时，遇到 FunctionDef 调用 _parse_function(is_method=False)，遇到 ClassDef 后遍历其 body 中的 FunctionDef 调用 _parse_function(is_method=True, parent_class=class_name)。

错误处理方面，我针对 SyntaxError 做了专门处理——如果 ast.parse() 抛出 SyntaxError（文件有语法错误），不抛异常，而是返回只包含文件级 chunk 的结果。这样索引过程不会因为一个坏文件而中断。这是 robustness 的体现。

Q11: ast_parser 中 _get_attr_name 递归函数是做什么的？

参考回答：

这个函数处理复合装饰器名称。比如 @pytest.mark.skip 在 AST 中不是一个简单的 Name 节点，而是 Attribute(value=Attribute(value=Name('pytest'), attr='mark'), attr='skip') 的嵌套结构。递归函数从最内层 Name 开始，逐层拼接 attr，最终还原出 pytest.mark.skip 的完整名称。如果不做这个处理，装饰器信息就会丢失，后续检索时无法利用装饰器的语义信息（比如 @pytest.mark.skip 说明这个测试被跳过了，可能和 Issue 有关）。

Q12: repo_indexer 中 hybrid_search 为什么要"过检索"(k*2)？

参考回答：

过检索是为了提高召回率。假设最终要返回 Top-5，如果向量和 BM25 各只取 5 个，那两者取并集最多 10 个候选。但可能存在这种情况：真正相关的 chunk 在向量检索中排第 6、在 BM25 中排第 8——都不在各自的 Top-5 中，但合并后可能进入总体 Top-5。各取 k*2（即 10 个）扩大了候选池，给了合并阶段更多选择。代价是多了几个候选的计算开销，但合并只是做加权求和，性能影响微乎其微。这是信息检索中经典的 recall-precision tradeoff——在这里选择了更高的 recall。

五、场景设计类问题

Q13: 如果仓库有 100 万行代码，现在的系统哪些地方会出问题？怎么解决？

参考回答：

几个瓶颈。第一，AST 解析现在是单进程串行的，100 万行可能要几分钟。解决方案是 multiprocessing + 文件级并行。第二，向量检索——ChromaDB 的 HNSW 索引在百万级向量下仍可用，但内存需求会增长。核心问题是 embedding 生成——每个 chunk 都要调用一次 Ollama，100 万行可能对应几万个 chunk，embedding 时间会很长。可以做增量索引（只对新/修改的文件重新 embedding），也可以换用更快的嵌入服务。第三，BM25 的倒排索引本身对百万文档是高效的（这是搜索引擎的基本功），但 jieba 分词是 CPU 密集型，可以预处理缓存。第四，LLM 上下文窗口——如果 Top-10 函数的代码加起来超过 4096 tokens，就需要做上下文压缩（只保留关键行、去掉注释等）。

Q14: 如果支持多语言（不只 Python），你会怎么设计？

参考回答：

核心改动在 ast_parser。现在的 ASTParser 是 Python 专用的，需要抽象出一个 LanguageParser 接口，每种语言各自实现。接口设计大概是这样：parse_file(language, source_code) -> List[CodeChunk]，其中 CodeChunk 是语言无关的数据结构。对于 Python 用 ast 模块，对于 JavaScript/TypeScript 可能需要用 tree-sitter 做 AST 解析，对于 Java 可能用 javalang。嵌入模型也要考虑多语言——现在的 nomic-embed-text 对非英文代码的语义理解可能不好，可以换成 multilingual-e5 或 CodeBERT。BM25 的分词器也要语言适配——jieba 是中文分词，英文用空格分词就够了。

Q15: 如果部署到生产环境，还需要做哪些改造？

参考回答：

第一，任务队列。现在分析请求是同步的（虽然用了异步 API 模式，但任务在同一个进程中执行），生产环境需要 Celery + Redis 做异步任务队列，支持任务重试和优先级。第二，数据库持久化——任务状态从内存字典迁移到 PostgreSQL/MySQL，支持查询历史记录。第三，LLM 服务高可用——Ollama 单实例不可靠，需要部署多个实例 + 负载均衡，或者切到 OpenAI/Anthropic 的 API（有 SLA 保障）。第四，安全和隔离——subprocess 执行测试代码有安全风险，需要 Docker 沙箱隔离。第五，监控——接入 Prometheus + Grafana，监控 LLM 调用延迟、检索 QPS、Patch 成功率等指标。第六，CI/CD 集成——做成 GitHub App 或 GitLab CI plugin，让开发者直接在 PR 中触发分析。

面试心态建议

校招面试中，面试官更看重 「你理解问题有多深」而不是「你用了多少工具」。与其罗列技术栈，不如深入讲一个模块的设计——比如混合检索中为什么需要归一化、怎么处理边界情况、实践中遇到了什么问题。展现"我做了工程权衡"比展现"我会调用 API"重要一百倍。

记住这个公式：我做了什么 → 为什么这样做（和其他方案的 trade-off）→ 如果重来会改进什么。这个三段式回答几乎适用于所有面试题。
