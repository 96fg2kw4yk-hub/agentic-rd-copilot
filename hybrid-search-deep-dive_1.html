混合检索为什么是「三路」？

以下用本项目索引的 requests 库源码做真实对比，Issue："用户登录后偶发 500，日志显示 JWT decode failed"

一、核心问题：代码不是自然语言

搜索引擎和 RAG 系统的默认假设是 "文本就是自然语言"。但代码不是。代码里有大量独有特征，让纯向量检索和纯关键词检索各自有盲区：

代码特征

精确标识符

驼峰/下划线命名

大量缩写

层级结构（文件→类→方法）

import 依赖关系

装饰器/注解

错误码（500、404）

同名不同义（token 变量 vs token 认证）

纯向量检索的盲区

对缩写不敏感（auth vs authentication 可能拉开距离）

对精确名称匹配弱（jwt_decode 和 decode_jwt 语义一样但向量不一定最近）

对错误码不敏感（500 只是个数字）

无法利用文件层级结构

纯 BM25 的盲区

无法处理同义词（"登录"和 authenticate 没有共同词）

对拼写变体敏感（color vs colour 完全不同的词）

无法理解上下文（"JWT"在注释中 vs 在代码逻辑中，BM25 区分不了）

忽略语义相近的代码（try-except 和 error handling）

核心洞察：BM25 和向量检索的盲区恰好 互补——BM25 擅长的事（精确符号匹配）正是向量检索的弱点，向量检索擅长的事（语义理解）正是 BM25 的弱点。这就是混合检索的根本动机——不是"两个不够再加一个"，而是"每个补另一个的短板"。

二、场景拆解：同一条 Issue，三路各自看到了什么

Issue："用户登录后偶发 500，日志显示 JWT decode failed"

这条 Issue 包含几种信息：场景词（登录）、错误码（500）、精确术语（JWT、decode）、业务领域（认证）。

🔹 BM25 看到了什么

保留的词（经过分词和停用词过滤后）：

JWT、decode、failed、登录、500、日志

BM25 用这些词在倒排索引中查，看哪些 chunk 包含了这些词，以及词频有多高。

排名BM25 找出的 chunk分数分析
1 requests/auth.py — HTTPBasicAuth.__call__
包含 "auth" 多次，且有 import base64（与 decode 语义关联弱）		 0.85 ✔ 文件对，关注认证逻辑
2 requests/utils.py — get_encoding_from_headers

BM25 的问题：排第 3 的 iter_content 只是因为函数体里有 decode 这个词（巧合），跟 JWT 认证毫无关系。排第 4 的 status_codes.py 命中了 "500"，但它是静态字典，不是 Bug 源头。BM25 只看词频不看语义，只要有词命中就加分，不管这个词在上下文中是否真的相关。

向量检索的优势：排第 3 的 Session.request 函数名里没有任何 "decode" "JWT" 字样，但语义上它是 500 错误的实际抛出位置——用户发请求 → Session 处理 → 响应 500，这是语义理解的功劳。BM25 根本找不到这个关联。

但向量检索也有问题：requests/cookies.py 没出现在 Top-5（BM25 把它排到了第 5），因为它在语义上跟 "登录失败" 不相关。这说明向量检索 自动过滤了 BM25 的词频噪音——但代价是，如果 Issue 里精确提到了一个冷门函数名（比如 _basic_auth_str），向量检索可能因为该函数的语义和 Issue 不够"近"而排到很后面，而 BM25 会因为精确词命中直接排到第一。这两种失效模式正好相反。

三、为什么还要加第三路「结构化分数」？

BM25 和向量检索都在"文本内容"层面竞争，它们共享同一个盲区：看不到代码的结构信息——文件路径、函数命名约定、import 关系。这些不是从文本内容能推断出来的，但它们对代码检索很重要。

结构化分数具体加了什么

# repo_indexer.py hybrid_search 中的结构化评分逻辑（第 314-325 行）
query_lower = query.lower()         # "jwt decode failed 登录 500"

for chunk_id, info in combined.items():
    sn = doc.metadata["symbol_name"]   # 函数名，如 "HTTPBasicAuth"
    fp = doc.metadata["file_path"]     # 文件路径，如 "requests/auth.py"

    structural = 0.0

    for word in query_lower.split():
        # 规则 1: Issue 中的词命中了函数名 → strong signal
        if word in sn.lower():
            structural += 0.3
        # 规则 2: Issue 中的词命中了文件路径 → medium signal
        if word in fp.lower():
            structural += 0.2

    # 规则 3: 文件路径含 "test" → 微微降权（不是 Bug 位置，而是测试）
    if "test" in fp.lower():
        structural += 0.1

    # 封顶 0.5（防止叠加过多）
    info["structural_score"] = min(structural, 0.5)

但它从向量检索中拿到了高分（语义上相关），最终分数不会被拖垮

这其实就是一种隐式的 "降噪"——没有结构信号支持
tests/test_auth.py::test_basic_auth "auth" 在路径 + "test" 触发规则 3 0.3 测试文件相关但非 Bug 源头，给中等分
第三路的核心价值：它不依赖 LLM，不依赖 embedding 模型，纯规则、零成本、毫秒级。它把 代码领域的人类先验知识（"Issue 提到 auth 时 auth.py 文件应该加分"）编码进了检索系统。而且它只影响最终分数的 20%，不会压倒前两路信号——相当于一个"纠偏项"而不是主导项。

四、4:4:2 权重是怎么来的？

这不是数学推导，而是 实验驱动的经验值。思路是：

BM25 和向量各 40%：两者是最核心的检索信号，且互补性最强。一个擅长精确、一个擅长语义。Giving them equal weight 是对两者都信任的表现——不说谁比谁更重要。

结构化 20%：它是一个辅助信号，作用是微调而非主导。如果给它太高权重（比如 40%），会出现 "Issue 说什么文件，系统就只返回那个文件" 的过拟合——路径匹配会压倒语义理解。给它 20%，足够在有明显路径信号时纠偏，但不会主导排序。

生产环境怎么做：这三个权重应该通过 learning-to-rank 或 grid search + 评测集 来调优。项目里 benchmark.py 已经提供了评测框架——在不同权重组合下跑 Top-K 准确率和 MRR，选最好的。面试时说 "目前是经验值，但框架支持数据驱动的权重学习" 比 "这权重是最优的" 要诚实得多，也更加分。

五、面试话术：如果被问到「你的混合检索是怎么设计的」

推荐回答结构（1-2 分钟）：

第一层（Why）："纯向量检索在代码场景有两个问题——对精确标识符匹配弱、对领域特定术语（如错误码）不敏感。纯 BM25 反过来，对语义同义词无感。两者的盲区恰好互补，所以我做了三路混合。"

第二层（How）："BM25 负责精确符号匹配，用 jieba 分词后建倒排索引；向量检索用 ChromaDB + Ollama embedding 做语义搜索，两个各取 k*2 候选。合并时先做 max-normalization 归一化到 [0,1]，再按 4:4:2 加权求和。第三路结构化分数是我人工编码的代码领域先验——函数名匹配加 0.3，路径匹配加 0.2，纯粹基于规则。"

第三层（Insight）："归一化是关键——BM25 的值域和向量距离完全不同，不做归一化的话一个信号会淹没另一个。另外 k*2 过检索是为了提升召回率，给合并阶段更大的候选池。权重 4:4:2 目前是经验值，框架支持在评测集上做 grid search 或 learning-to-rank 来学习最优权重。"

六、边界情况：什么时候混合检索也会失效？

场景 1：Issue 全是业务语言，没有技术关键词

比如 "点击保存按钮后页面卡住了"。BM25 找不到任何代码中的词（"保存按钮" 不在代码里），向量检索可能匹配到 save/click handler，但精度很低。结构化分数也加不了分（Issue 里没有文件路径信息）。

解决方法：Issue 分析 Agent 要用 LLM 把业务语言翻译成技术关键词（"保存按钮" → "onClick" "save()" "persist"）。这是 V2 的改进方向。

场景 2：Bug 在 import 的第三方包里

比如 Bug 实际是 urllib3 的 bug，但 Issue 报在 requests 上。混合检索只能在 requests 的索引里搜，找不到 urllib3 的代码。

解决方法：索引时要沿 import 链拓展索引范围。或者 Bug 定位 Agent 分析时如果发现 Top 结果都不够好，可以建议 "Bug 可能在依赖库中"。

场景 3：同一仓库中有大量同义词

比如一个微服务项目中有 5 个 auth 模块（auth_service、auth_client、auth_middleware、auth_utils、auth_admin），Issue 只说 "auth 有问题"。三路检索都会把 5 个模块都排在前面，区分度不够。

解决方法：需要更细粒度的结构化信息——比如 import 依赖图、模块间的调用关系——来打破并列局面。这需要 AST 解析扩展到跨文件分析。
